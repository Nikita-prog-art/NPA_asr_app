# NPA ASR — GigaAM-v3 e2e_rnnt на ggml

Кроссплатформенное (Windows + Linux) приложение для распознавания русской речи
моделью [`ai-sage/GigaAM-v3`](https://huggingface.co/ai-sage/GigaAM-v3)
(revision `e2e_rnnt`) на экосистеме **ggml** (llama.cpp / ggml / whisper.cpp):
свой Conformer-энкодер и RNN-T-декодер на графах ggml, без Python и без
libtorch в рантайме.

* **Push-to-talk**: зажали сочетание клавиш — пошла запись и **потоковая**
  транскрибация (текст появляется уже через ~0.7–1 с, а не после отпускания).
* **Сворачивается в трей** (Windows): крестик прячет окно, распознавание и
  сочетание клавиш продолжают работать, значок рядом с часами возвращает окно и
  умеет выйти. Явная кнопка «Выход» есть внизу «Настроек».
* **Настройка числа потоков** (по умолчанию — половина логических ядер, см.
  раздел «Про потоки и почему «авто» — это половина ядер» ниже),
  тёмная/светлая темы.
* **Скачивание модели** нужного уровня квантизации прямо из приложения (или
  указание пути к своему `.gguf`).
* Финальный текст **вставляется в активное окно** и дублируется в буфер обмена.
* **Один самодостаточный исполняемый файл**: всё, что мы собираем сами (ggml,
  imgui, glfw, ядро распознавания), линкуется статически; на Windows это ещё и
  статический CRT (`/MT`), поэтому VC++ Redistributable не нужен. На Linux
  остаются только системные библиотеки (libX11/libGL/libcurl).
* Таргет под архитектуру процессора с фолбеком: по умолчанию `ASR_CPU_ARCH=x86-64-v3`
  (AVX2/FMA/F16C/BMI2 — любой Intel с 2013 г. и любой AMD Zen), `ASR_CPU_ARCH=native`
  — максимум для машины сборки, `x86-64-v2`/`x86-64` — для старого железа.
  Если CPU не умеет нужное, приложение печатает понятную ошибку вместо SIGILL.
* **Масштаб интерфейса**: автоматически по DPI монитора (per-monitor v2 на
  Windows) плюс ручной `Ctrl +` / `Ctrl -` / `Ctrl 0` (шаг 5 %).
* **Установка в профиль и автозапуск** одной кнопкой (`--install`).

## 1. Что уже проверено

Численная эквивалентность эталонной PyTorch-реализации (тот самый
`modeling_gigaam.py` с Hugging Face) проверена по шагам:

| Проверка | Результат |
|---|---|
| log-mel фронтенд против `torchaudio` | `max_abs = 4.1e-05` |
| энкодер целиком (`enc`, 16 слоёв) | `max_abs = 1.2e-03` при диапазоне ±2.4 |
| промежуточные слои 0…15 | совпадают (ошибка ≤ 1.5e-02 на значениях до ±200) |
| предиктор (embedding + LSTM) | `max_abs = 6e-08` |
| joint-сеть (сырые логиты) | `max_abs = 1.5e-02` |
| **итоговые токены** (жадное декодирование) | **те же**, что у PyTorch |
| текст на 3 тестовых файлах | совпадает с эталоном, включая пунктуацию и нормализацию чисел |

Примеры (TTS-файлы 16 кГц, синтез русским голосом Windows):

```
«Привет, это тест распознавания речи.»
  → Привет. Это тест распознавания речи.

«Сегодня хорошая погода, давайте проверим, как работает потоковое распознавание речи на русском языке.»
  → Сегодня хорошая погода. Давайте проверим, как работает потоковое распознавание речи на русском языке.

«Запиши встречу на пятнадцатое марта в четырнадцать тридцать.»
  → Запиши встречу на 15 марта в 14:30.
```

Скорость на i9-13900HK (8 потоков, `f16`, статическая сборка `x86-64-v3`):
**~10× реального времени** — 903 мс на 8.98 с аудио (Linux) и 902 мс (Windows),
мел-фронтенд ~30 мс (3 %), энкодер ~810 мс (90 %). Модель 222.5M параметров,
445 МБ в `f16`.

Что даёт и что не даёт выбор ISA и OpenMP (тот же файл 8.98 с, 8 потоков,
`asr_test bench`, 3 итерации):

| Сборка | энкодер | всего | ×RT |
|---|---|---|---|
| `x86-64-v3` (по умолчанию), без OpenMP | 801–815 мс | 903–930 мс | 9.7–9.9 |
| `x86-64-v3` + `ASR_OPENMP=ON` | 789–822 мс | 864–913 мс | 9.8–10.4 |
| `native` (AVX2 + AVX-VNNI этого CPU) | 795–834 мс | 902–943 мс | 9.5–10.0 |
| старая динамическая сборка (`alderlake` + OpenMP) | 857 мс | 896 мс | 10.0 |

Разница внутри шума: `-march=native` и OpenMP не дают ничего заметного (AVX-VNNI
ускоряет только целочисленные `q8_0`/`q4_0`-ядра, а модель по умолчанию `f16`),
поэтому по умолчанию — переносимый `x86-64-v3` без лишних зависимостей.

Качество и скорость квантизаций измерены отдельно, на 356 реальных фразах —
см. [«Что теряется при квантизации»](#что-теряется-при-квантизации): по
умолчанию предлагается `q4_0` (в 2.5 раза меньше `f16`, ~10 % быстрее, WER в
пределах разброса).

Поведение «крестик → трей» проверено на Windows 11 автотестом через сообщения
окна: закрытие прячет окно и процесс остаётся жив, команда значка возвращает
окно, «Выход» из меню завершает процесс с кодом 0. Значок в проводнике, иконка
на панели задач сразу после запуска (без похода в трей) и русские пункты меню
трея проверены скриншотами. На Linux трей недоступен, и крестик по-прежнему
закрывает приложение — это состояние проверено скриншотом вкладки «Настройки».

## 2. Как это устроено

```
микрофон ──► кольцевой буфер ──► log-mel (320-точечный FFT: oneMKL DFTI или свой Bluestein)
                                      │
                                      ▼
                     Conformer-энкодер на ggml (16 слоёв)
                     subsampling conv1d ×2, rotary self-attention,
                     conv-модуль (depthwise + LayerNorm), FFN ×2
                                      │
                                      ▼
                     RNN-T: предиктор (embedding + LSTM) + joint
                     покадровое жадное декодирование (max 10 символов/кадр)
                                      │
                                      ▼
                     SentencePiece (словарь зашит в GGUF) ──► текст
```

**Про потоковость.** RNN-T-декодер потоковый по своей природе (он покадровый),
но Conformer-энкодер этой модели обучен с полным (не причинным) вниманием,
поэтому «настоящего» причинного стриминга у модели нет. Приложение использует
скользящее окно с локальным согласованием (LocalAgreement-2, как в
whisper-stream):

* пока запись идёт, каждые `step_sec` (по умолчанию 1 с) окно последних
  `max_window_sec` (по умолчанию 20 с) перекодируется целиком — то есть
  внимание остаётся ровно таким, как при обучении, качество не теряется;
* стабильный префикс токенов (совпавший с предыдущим окном) «коммитится» и
  показывается как готовый текст, хвост — как предварительный;
* по отпусканию клавиши делается финальный проход и текст точный.

Короткие реплики (до 20 с — обычный push-to-talk) всегда кодируются целиком,
так что финальный результат совпадает с офлайн-распознаванием.

### Про потоки и почему «авто» — это половина ядер

Режим «авто» (и значение по умолчанию для `-t`) — `max(1, логических ядер / 2)`.
Причина практическая: пул потоков ggml крутится в барьерах на спинлоках, и один
воркер на логический процессор переподписывает гибридные CPU (P-ядра + E-ядра,
например 20 логических на 14 физических): при переходе питания на «экономный»
или под нагрузкой от других приложений энкодер может «зависнуть» на десятки
минут, бесконечно прогоняя один и тот же граф. Половина логических ядер
оставляет загрузку всех ядер, но убирает переподписку.

Если хочется быстрее — поднимайте число потоков вручную («Настройки» → ползунок
«Потоки» или `-t N`), но следите за временем: на 20 потоках эта машина
периодически уходит в такой штопор. Значение по умолчанию в GUI можно вернуть
галочкой «авто».

## 3. Сборка

### Linux

```bash
scripts/build_linux.sh                 # gcc, статический бинарник build/bin/npa_asr
ASR_CPU_ARCH=native scripts/build_linux.sh  # максимум для этой машины (без фолбека)
ASR_CPU_ARCH=x86-64-v2 scripts/build_linux.sh  # для CPU до 2013 года
ASR_JOBS=6 scripts/build_linux.sh      # ограничить параллелизм (см. про память ниже)
```

Результат — **один файл** `build/bin/npa_asr`; рядом никаких `.so` не появляется
(`ldd` показывает только системные библиотеки).

Зависимости: `cmake`, `ninja`, `libx11-dev`, `libxtst-dev`, `libxrandr-dev`,
`libxinerama-dev`, `libxcursor-dev`, `libgl1-mesa-dev`, `libcurl4-openssl-dev`
(ggml/miniaudio/imgui/glfw скачиваются CMake-ом автоматически,
`-DASR_FETCH_DEPS=OFF` — если хотите положить их руками).
`-DASR_LIBCURL=OFF` убирает и libcurl: загрузка моделей тогда идёт через
внешний `curl`/`wget`, а список динамических зависимостей сжимается до
X11/OpenGL/libc.

### Windows

```cmd
scripts\build_windows.cmd              :: MSVC, статический npa_asr.exe
set ASR_CPU_ARCH=native && scripts\build_windows.cmd
set ASR_NATIVE=ON && scripts\build_windows.cmd
```

Скрипт находит Visual Studio через `vswhere` и собирает
`build-windows\bin\npa_asr.exe`. Рядом с exe **не нужно ничего**: ggml, GLFW и
CRT вкомпилированы (проверяется `dumpbin /dependents` — только системные
`KERNEL32/USER32/GDI32/OPENGL32/WINHTTP/...`). Релизы собираются в CI:
`.github/workflows/release.yml` (по тегу `v*`), ручная сборка ветки —
`build.yml` (только `workflow_dispatch`, чтобы не гонять CI на каждый пуш).

Если разработка идёт в WSL (как у автора), удобнее собрать Windows-версию
оттуда — MSVC не умеет работать по UNC-пути, поэтому скрипт упаковывает исходники
в один tar, распаковывает на хост и запускает обычную сборку:

```bash
scripts/build_windows_from_wsl.sh          # WIN_BUILD_DIR=C:\dists\builds\npa_asr_build
```

### Почему без oneAPI и без рантайм-диспатча ggml

oneAPI/oneMKL из проекта убран (вместе с `cmake/oneapi.cmake`, `ASR_MKL_FFT` и
`ASR_COMPILER=icx`). Измерено на i9-13900HK (8 потоков, `asr_test bench`, файл
8.98 с; gcc-бинарь запускался без `LD_LIBRARY_PATH` oneAPI, icx — со своими
runtime-библиотеками):

| Сборка | мел-фронтенд | энкодер (10 итераций × 3 прогона) | всё распознавание |
|---|---|---|---|
| gcc 14 + oneMKL DFTI | 33.8 мс (3.8 %) | 857 мс (856/856/857) | 896 мс (10.0× RT) |
| gcc 14 + свой FFT (Bluestein) | 35.4 мс (3.8 %) | 857 мс | 923 мс (9.7× RT) |
| icx/icpx 2025.3 + Intel OpenMP | 28–31 мс | 876 мс (840–910) | 1015 мс (8.8× RT) |

* **oneMKL ускоряет только FFT, а FFT — это ~4 % времени**, то есть итоговый
  выигрыш ≈ 0.2 %. При этом линковка oneMKL тянет зависимость от окружения
  oneAPI в рантайме: на Windows exe без `setvars.bat` падал с «не обнаружена
  mkl_rt.2.dll», на Linux в процесс отображается ~100 МБ библиотек MKL.
* **icx/icpx + Intel OpenMP не быстрее gcc 14** (скорее на ~2 % медленнее и
  заметно менее стабилен по времени): ядра ggml написаны интринсиками вручную,
  компилятору почти нечего улучшать.
* **Рантайм-диспатч ggml (`GGML_CPU_ALL_VARIANTS` + `GGML_BACKEND_DL`) убран
  вместе с динамической линковкой**: он требовал 14 файлов `ggml-cpu-*.so/.dll`
  рядом с exe, что несовместимо с «одним статическим файлом». Вместо него ISA
  фиксируется на этапе конфигурации (`ASR_CPU_ARCH`). Для `f16`-модели разницы
  между вариантами `alderlake` и `haswell` практически нет — AVX-VNNI ускоряет
  только целочисленные (`q8_0`/`q4_0`) скалярные произведения.
* **OpenMP тоже убран** (`ASR_OPENMP=OFF`): ggml использует собственный пул
  потоков, libgomp/vcomp140.dll в зависимостях не появляется, а по скорости
  вариант с OpenMP не выигрывает (см. замеры в разделе про производительность).

Реальные рычаги производительности — число потоков (`--threads`, в GUI ползунок)
и `ASR_CPU_ARCH=native` (сборка под конкретный CPU).

### Про память при сборке

`GGML_CPU_ALL_VARIANTS` собирает `ggml-cpu` по разу на каждый вариант ISA, и
большие TU (`ggml-cpu/ops.cpp` с AVX512) требуют ~2 ГБ ОЗУ каждый. Поэтому
скрипты считают `-j` как `min(ядра, ОЗУ_ГБ/2)`; переопределяется через
`ASR_JOBS`. Без этого `-j20` на 16-гигабайтной WSL легко съедает всю память и
вешает дистрибутив (проверено на себе). Если памяти всё равно мало, добавьте в
`%UserProfile%\.wslconfig`:

```ini
[wsl2]
memory=24GB
swap=8GB
```

## 4. Модель

Три способа получить веса:

1. **Скачать из приложения** (вкладка «Модели» → «Каталог моделей»): приложение
   читает `models/manifest.json` из репозитория/релиза, показывает доступные
   квантизации и качает выбранную с проверкой SHA-256; рекомендуемая
   квантизация помечена и стоит в списке первой.
   Чтобы файлы появились, один раз запустите workflow
   `.github/workflows/convert-model.yml` (Actions → Run workflow): он скачает
   `pytorch_model.bin` (449 МБ) с Hugging Face, сконвертирует в GGUF
   (`f16`, `q8_0`, `q5_0`, `q4_0`), опубликует их как release assets и обновит
   `models/manifest.json` в репозитории. Вход `recommend` (по умолчанию `q4_0`)
   выбирает квантизацию, которую приложение советует.
2. **Сконвертировать самому** (Python, ~1 минута):
   ```bash
   python -m pip install torch --index-url https://download.pytorch.org/whl/cpu
   python -m pip install gguf==0.19.0 numpy sentencepiece
   # config.json, tokenizer.model, pytorch_model.bin из revision e2e_rnnt
   python tools/convert_gigaam_to_gguf.py \
       --model-dir models/hf/gigaam-v3-e2e_rnnt \
       --out models/gguf/gigaam-v3-e2e_rnnt-q4_0.gguf --quant q4_0 \
       --manifest models/manifest.json --recommend
   ```
   Версия `gguf` зафиксирована намеренно: у неё квантованный тензор передаётся
   в байтовой форме (`add_tensor(..., raw_dtype=...)`), и именно на этом ломался
   конвертер при `gguf` из `main` (ошибка «bytes per row (768) is not a multiple
   of Q8_0 type size (34)»).
3. **Указать путь** к любому готовому `.gguf` (вкладка «Модели» → поле пути или
   перетаскивание файла в окно).

Уровни квантизации: `f16` — точная копия оригинальных весов (энкодер в
чекпоинте и так fp16), `q8_0`/`q5_0`/`q4_0` — меньше размер, чуть быстрее;
декодер, joint-сеть и мел-фильтрбанк всегда остаются fp32.

### Что теряется при квантизации

Один и тот же набор — **356 реальных фраз** из FLEURS ru_ru (dev, 1.08 ч аудио,
разные дикторы, новостной домен) — прогнан всеми четырьмя уровнями на одной
машине (i9-13900HK, 10 потоков, `asr_test batch`); CER/WER считает
`tools/score_asr.py` против эталонных расшифровок, интервал — парный бутстрап по
фразам (`--ci`):

| Модель | Размер | CER | WER | Фраз без ошибок | WER − `f16` (95 %) |
|---|---|---|---|---|---|
| `f16` | 449 МБ | 1.60 % | 4.78 % | 59.0 % | — |
| `q8_0` | 272 МБ | 1.61 % | 4.83 % | 59.0 % | +0.05 п.п. [−0.02; +0.12] |
| `q5_0` | 201 МБ | 1.62 % | 4.94 % | 57.0 % | +0.15 п.п. [0.00; +0.31] |
| `q4_0` | **177 МБ** | 1.60 % | 4.92 % | 57.6 % | +0.14 п.п. [−0.06; +0.34] |

Скорость на том же CPU (файл 34.09 с, 10 потоков, 5 итераций, два прогона):

| Модель | энкодер | всё распознавание | ×RT |
|---|---|---|---|
| `f16` | 2900–3253 мс | 3523–3693 мс | 9.2–9.7 |
| `q8_0` | 2573–2764 мс | 2924–3130 мс | **10.9–11.7** |
| `q5_0` | 3229–3363 мс | 3678–3820 мс | 8.9–9.3 |
| `q4_0` | 2840–2973 мс | 3293–3364 мс | 10.1–10.4 |

Выводы:

* **`q4_0` — то, что стоит брать по умолчанию**: файл в 2.5 раза меньше `f16`,
  на ~10 % быстрее, а разница WER (+0.14 п.п.) меньше, чем разброс на 356 фразах
  — интервал накрывает ноль. Именно он помечен как рекомендуемый в каталоге
  моделей (`"recommended": true` в `models/manifest.json`, workflow принимает
  `recommend`).
* `q8_0` — «перестраховочный» вариант: статистически неотличим от `f16`
  (+0.05 п.п. [−0.02; +0.12]) и самый быстрый, но в 1.5 раза больше `q4_0`.
* `q5_0` **проигрывает по всем трём параметрам сразу**: больше `q4_0`, медленнее
  даже `f16` и WER чуть выше (у `x86-64-v3` нет AVX-VNNI, а `q5_0`-ядра ggml
  оптимизированы хуже, чем `q4_0`/`q8_0`). В каталоге он остаётся, но
  рекомендуемым не помечен; из набора его можно убрать, перечислив нужные
  квантизации во входе `quants` workflow.
* Численно энкодер от квантизации страдает заметно — `max_abs` против PyTorch на
  том же файле: `1.3e-03` у `f16`, `4.8e-02` у `q8_0`, `3.1e-01` у `q5_0`,
  `7.0e-01` у `q4_0` (значения энкодера в диапазоне ±2.4). Декодер и joint-сеть
  остаются fp32, поэтому в текст это почти не переходит: энкодер устойчив к шуму
  весов. На двух TTS-файлах с эталонными токенами (`medium`, `numbers`) все
  четыре уровня дают **токены, идентичные PyTorch**.

## 5. Использование

### GUI

```bash
./build/bin/npa_asr            # или npa_asr.exe
```

Зажмите **Ctrl+Alt+Space** (настраивается, в том числе «записать сочетание» в
настройках) или кнопку «Удерживайте для записи» мышью. Текст появляется на
экране по мере распознавания, по отпусканию вставляется в активное окно и
кладётся в буфер обмена (режим вывода настраивается: в окно + буфер / только
буфер / только в окне).

**Масштаб интерфейса.** По умолчанию окно подстраивается под DPI монитора
(на Windows приложение объявлено per-monitor-DPI-aware через манифест, поэтому
при 125 %/150 % интерфейс остаётся резким, а не растянутым). Вручную:
`Ctrl +` / `Ctrl -` (шаг 5 %), `Ctrl 0` — вернуться к автомату; то же самое
есть в «Настройки» → «Окно и оформление» (кнопки `-`/`+` и галочка «авто»).
Выбранное значение сохраняется в `settings.json`.

**Поведение окна.** «Поверх остальных окон» по умолчанию **выключено**: иначе
окно висело над всеми приложениями и не уходило с дороги, когда вы переключаетесь
в редактор, куда диктуете.

**Трей.** На Windows крестик не закрывает приложение, а прячет окно: значок
остаётся рядом с часами, сочетание клавиш работает, диктовка в другие окна
продолжается. Значок в трее по левому щелчку возвращает окно, по правому даёт
меню «Открыть окно» / «Выход». Полностью выйти можно и кнопкой «Выход» внизу
вкладки «Настройки», и `Ctrl+C` в консольном режиме. Windows 11 по умолчанию
прячет новые значки в переполнение — стрелка `^` слева от иконок, там наш значок
(синий квадрат с белыми полосками) можно перетащить на панель.

Значок один и тот же в проводнике, на панели задач, в заголовке окна и в трее. Он
рисуется кодом (`app_icon_rgba`), а на этапе сборки та же функция превращается в
ресурс `.exe` (`tools/make_icon.cpp`) — так в репозитории нет бинарных файлов, а
иконка не может «отстать» от остальных. Окно создаётся скрытым и показывается уже
с зарегистрированным значком: панель задач строит кнопку при первом показе, и
окно, которое `glfwCreateWindow()` показывает само, оставалось бы с системной
иконкой GLFW до первого скрытия и повторного показа.

На Linux системного трея нет (у панелей X11 нет единого протокола для этого), и
крестик закрывает приложение, как раньше — в интерфейсе это написано прямо в
разделе «Завершение работы».

**Установка.** При первом запуске приложение предлагает скопировать себя в
личную папку и добавить в автозагрузку; позже то же самое доступно внизу
вкладки «Настройки», в разделе «Установка приложения» (или флагами `--install`,
`--uninstall`, `--autostart on|off`, `--install-status`). Когда запускается
сборка с другой ревизией исходников, приложение один раз предлагает обновить
установленную копию — см. [«Установка и автозапуск»](#установка-и-автозапуск).

### CLI

```bash
npa_asr -m model.gguf -i audio.wav          # офлайн-распознавание файла
npa_asr -m model.gguf -i audio.wav --stream # эмуляция потока кусками по 100 мс
npa_asr -m model.gguf --mic                 # push-to-talk без GUI
npa_asr --list-devices                      # устройства захвата
npa_asr --list-models                       # локальные .gguf
npa_asr --download                          # скачать рекомендуемую квантизацию (q4_0)
npa_asr --download --quant q8_0             # ...или конкретную
npa_asr --info                              # CPU-базлайн, потоки, каталоги
npa_asr --install-status                    # состояние установки/автозапуска
```

### Горячие клавиши на Linux

* **X11 (в т.ч. WSLg)**: по умолчанию используется XRecord — сочетание
  *наблюдается*, но не перехватывается у других приложений. Если libXtst
  недоступна, приложение падает на `XGrabKey` (тогда сочетание забирается себе).
* **Wayland**: глобальных хоткеев без порталов нет, поэтому используется
  чтение `/dev/input/event*` (evdev). Нужно добавить пользователя в группу
  `input`: `sudo usermod -aG input $USER` и перелогиниться.
* Вставка текста на Linux делается через XTest (libXtst) в активное окно; если
  библиотеки нет — текст остаётся в буфере обмена, вставляется вручную.

Тесты и эталоны (нужен Python-venv с torch). `ref_gigaam.py` прогоняет

```bash
python -m venv .venv && .venv/bin/pip install torch --index-url https://download.pytorch.org/whl/cpu
```


## Установка и автозапуск

Приложение собирается в один самодостаточный исполняемый файл, поэтому
«установка» — это копирование его в пользовательский каталог и, по желанию,
регистрация в автозапуске. Настройки и модели при установке, удалении и
переключении автозапуска не трогаются: они всегда остаются в каталоге
пользовательских данных (`~/.local/share/npa_asr` в Linux,
`%LOCALAPPDATA%\npa_asr` в Windows).

Пути установки:

* **Windows**: `%LOCALAPPDATA%\Programs\NPA ASR\npa_asr.exe`;
  * автозапуск — раздел реестра
    `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, значение `NPA ASR`
    с данными `"<каталог установки>\npa_asr.exe" --minimized`.
* **Linux**: `~/.local/bin/npa_asr`;
  * автозапуск — `~/.config/autostart/npa-asr.desktop`;
  * пункт меню — `~/.local/share/applications/npa-asr.desktop`.

Флаги командной строки (работают без графического окружения; при ошибке
возвращается ненулевой код):

| Флаг | Действие |
| --- | --- |
| `--install` | скопировать приложение в каталог установки и включить автозапуск |
| `--install-only` | скопировать приложение без автозапуска |
| `--uninstall` | удалить автозапуск и установленные файлы (настройки и модели остаются) |
| `--uninstall-keep-files` | удалить только автозапуск, установленные файлы оставить |
| `--autostart on\|off` | включить или выключить автозапуск, не трогая установленную копию |
| `--install-status` | показать состояние: путь установки, ревизии установленной и запущенной сборок, актуальность копии, автозапуск |

```bash
npa_asr --install                 # копия в ~/.local/bin + автозапуск
npa_asr --install-only            # только копия
npa_asr --install-status          # что и где установлено
npa_asr --autostart off           # выключить автозапуск
npa_asr --uninstall               # удалить автозапуск и файлы
```

Чтобы команда `npa_asr` была доступна из терминала, каталог `~/.local/bin`
должен присутствовать в `PATH`; `--install-status` предупредит, если это не
так. Запуск установленной копии равносилен обычному запуску: повторная
установка поверх работающего процесса не выполняется (в Windows файл занят),
вместо этого выводится понятная ошибка.

### Когда приложение предлагает установку

В бинарник вшивается ревизия исходников (`ASR_BUILD_ID`, при сборке это
`git rev-parse --short HEAD`, плюс суффикс `-dirty`, если рабочее дерево было
изменено). Она видна в заголовке окна, в «О сборке», в `--info` и в
`--install-status`.

Предложение установки показывается **один раз на сборку**:

* если приложения ещё нет — при первом запуске;
* если установлена копия **другой ревизии** — при первом запуске новой сборки;
* если установлена копия **той же ревизии** (то есть код не изменился, файл
  просто пересобран) — предложения нет: обновлять нечего.

Ответ («Установить»/«Позже») запоминается вместе с ревизией в
`<каталог данных>/install.json`, поэтому повторные запуски одной и той же
сборки молчат. Ревизия установленной копии читается из самого файла (в
исполняемом файле есть строка-метка `npa-asr-build-id:<ревизия>`), а не из
отдельного файла состояния — иначе он бы разошёлся с реальностью, если
установленный файл заменить чем-то другим. Если метки в установленном файле
нет (копия поставлена старой версией), предложение появится один раз и
исчезнет после первого же обновления.

Сборка без репозитория `.git` (например, из архива исходников) получает
ревизию `unknown`: предложение тогда работает как «один раз на запуск сборки»,
а обновление всегда доступно вручную — внизу вкладки «Настройки». Ревизию можно
задать явно: `-DASR_BUILD_ID=<что угодно>`;
`scripts/build_windows_from_wsl.sh` делает это сам, потому что на Windows
исходники уезжают архивом без `.git`.
